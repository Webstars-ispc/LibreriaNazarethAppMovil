# GUIA DE LA CAPA RED - Librería Nazareth App Móvil

Esta guía explica cómo está armada la infraestructura de red de la app
y cómo usarla para agregar nuevos endpoints sin romper nada.
SI LES DA CONFLICTO ALGO NO MERGEAR, AVISAR Y SOLUCIONAMOS JUNTOS

================================================================================
1. ¿QUÉ ES ESTO?
================================================================================

Cuando la app necesita hablar con el backend (Django + MySQL), no puede
hacerlo directamente. Necesita:

  1. Saber a qué URL conectarse.
  2. Enviar y recibir datos en formato JSON.
  3. Incluir el token JWT en cada petición autenticada.
  4. Manejar errores de red de forma consistente.

Todo eso ya está resuelto en la carpeta `data/` del proyecto.
Solo tienen que USAR esas clases creadas, no reinventarlas.

================================================================================
2. ESTRUCTURA DE ARCHIVOS
================================================================================

app/src/main/java/com/example/librerianazareth/data/
│
├── NetworkConstants.java     → Constantes compartidas (URL base, claves, etc.)
├── RetrofitClient.java       → Punto de entrada. Devuelve el ApiService.
├── ApiService.java           → Interfaz con TODOS los endpoints de la API.
├── AuthInterceptor.java      → Agrega el token JWT a cada petición (automático).
│
├── local/
│   └── TokenManager.java     → Guarda/lee/borra los tokens JWT del dispositivo.
│
└── model/
    ├── LoginRequest.java     → Modelo para enviar email + password al login.
    └── LoginResponse.java    → Modelo con access + refresh que devuelve el login.

================================================================================
3. ¿PARA QUÉ SIRVE CADA ARCHIVO?
================================================================================

### NetworkConstants.java
Contiene constantes compartidas:
  - BASE_URL: la URL del backend (se lee desde local.properties).
  - HEADER_AUTHORIZATION: "Authorization"
  - TOKEN_PREFIX: "Bearer "
  - PREFS_AUTH, KEY_ACCESS, KEY_REFRESH: claves de SharedPreferences.

NO lo modifiques salvo que sepas lo que hacés.

### RetrofitClient.java
Es el punto de entrada. Se usa así:

    RetrofitClient.getApi(this)

Devuelve un objeto `ApiService` con todos los endpoints listos para llamar.
Es un singleton: una sola instancia para toda la app.

NO lo modifiques.

### ApiService.java
Es una INTERFAZ donde se declaran TODOS los endpoints de la API.
Actualmente incluye:
  - POST /api/auth/login/  → login(@Body LoginRequest)

Cada desarrollador AGREGA sus endpoints acá, sin borrar los de otros.
Ver sección 6 de este mismo archivo para saber cómo agregar uno.

### AuthInterceptor.java
Interceptor de OkHttp que agrega automáticamente la cabecera:
    Authorization: Bearer <token>
a cada petición, si hay un token guardado.

Esto significa que VOS NO TENÉS QUE PREOCUPARTE por el token.
Se agrega solo. Si no hay token (ej. antes del login), la petición
sale como anónima.

NO lo modifiques.

### TokenManager.java
Guarda y lee los tokens JWT desde SharedPreferences del dispositivo.

Uso:
    TokenManager tm = new TokenManager(context);
    tm.saveTokens(access, refresh);    // después del login
    String token = tm.getAccessToken(); // cuando lo necesites
    tm.clear();                         // en el logout
    boolean logueado = tm.isLoggedIn(); // chequeo rápido

NO lo modifiques.

### Carpeta model/
Contiene clases Java simples que representan las respuestas
y peticiones de la API.

Ya están:
  - LoginRequest   → { email, password }
  - LoginResponse  → { access, refresh }

Cada desarrollador AGREGA los modelos que necesite para sus endpoints.
Ver sección 7 de este mismo archivo para saber cómo.

4. CONFIGURACIÓN INICIAL (HACER UNA SOLA VEZ)
================================================================================

El backend y la base de datos YA ESTÁN EN LA NUBE (AlwaysData) y disponibles
24/7. NO hace falta levantar Django ni MySQL en tu PC. Solo tenés que apuntar
la app a la URL de AlwaysData.

### Paso 1: Editar local.properties

Abrí el archivo `local.properties` que está en la raíz del proyecto
(al lado de settings.gradle, NO dentro de app/).

Agregá (o reemplazá) esta línea:

    API_BASE_URL=https://librerianazareth.alwaysdata.net/

IMPORTANTE:
  - Termina en "/" (barra al final).
  - Usa "https://" (NO "http://").
  - NO lleva puerto (NO ":8000").
  - NO subas este archivo a Git (ya está en .gitignore).

### Paso 2: Sincronizar Gradle

Después de cambiar local.properties:
  - File > Sync Project with Gradle Files
  - Build > Clean Project
  - Build > Rebuild Project

Verificá que en `BuildConfig.java` (autogenerado) figure:
    public static final String API_BASE_URL = "https://librerianazareth.alwaysdata.net/";

### Paso 3: Verificar conexión

Desde el navegador del celular, abrí:

    https://librerianazareth.alwaysdata.net/api/

Si ves el API Root de Django REST Framework → todo OK.

También podés probar el admin:

    https://librerianazareth.alwaysdata.net/admin/

### Paso 4: Probar login en la app

Las credenciales de prueba se comparten por el canal privado del equipo. NO se publican en el repositorio por seguridad.

4.b (Opcional) BACKEND LOCAL PARA DESARROLLO
================================================================================

Si necesitás levantar el backend en tu PC (por ejemplo, para probar cambios
antes de subirlos a la nube), seguí estos pasos:

  1. Clonar el repo backend:
     git clone https://github.com/Webstars-ispc/LibreriaNazareth-Backend.git

  2. Crear .env con tus credenciales locales (XAMPP/MySQL).

  3. Levantar Django escuchando en toda la red:
     python manage.py runserver 0.0.0.0:8000

  4. Averiguar tu IP local (ipconfig en Windows).

  5. En local.properties poner:
     API_BASE_URL=http://TU_IP:8000/

  6. Verificar que la red de Windows esté en modo "Privada" y que el firewall
     permita el puerto 8000.

  7. Probar desde el navegador del celular:
     http://TU_IP:8000/admin/

⚠️ Recordá volver a `https://librerianazareth.alwaysdata.net/` cuando termines
   de probar localmente, para no romperle la conexión a tus compañeras.

5. CÓMO USAR LA INFRAESTRUCTURA (EJEMPLO DE LOGIN)
================================================================================

Supongamos que querés implementar el login. En tu LoginActivity:

    // 1. Obtener el ApiService
    ApiService api = RetrofitClient.getApi(this);

    // 2. Crear el request
    LoginRequest request = new LoginRequest(email, password);

    // 3. Llamar al endpoint
    api.login(request).enqueue(new Callback<LoginResponse>() {
        @Override
        public void onResponse(Call<LoginResponse> call,
                               Response<LoginResponse> response) {
            if (response.isSuccessful() && response.body() != null) {
                // 4. Guardar los tokens
                new TokenManager(LoginActivity.this).saveTokens(
                    response.body().getAccess(),
                    response.body().getRefresh()
                );

                // 5. Navegar a la siguiente pantalla
                startActivity(new Intent(LoginActivity.this, MainActivity.class));
                finish();
            } else {
                // Error HTTP (401, 400, 500...)
                Toast.makeText(LoginActivity.this,
                    "Credenciales incorrectas (código " + response.code() + ")",
                    Toast.LENGTH_LONG).show();
            }
        }

        @Override
        public void onFailure(Call<LoginResponse> call, Throwable t) {
            // Error de red (sin conexión, timeout, etc.)
            Toast.makeText(LoginActivity.this,
                "Error de conexión: " + t.getMessage(),
                Toast.LENGTH_LONG).show();
        }
    });

Eso es TODO. No hay que armar URL, ni agregar token, ni parsear JSON.
La infraestructura se encarga.

6. CÓMO AGREGAR UN NUEVO ENDPOINT
================================================================================

Seguí estos 3 pasos:

### Paso 1: Crear el modelo (si no existe)

En `data/model/`, creá una clase Java para el request y/o response.

Ejemplo para productos:

    package com.example.librerianazareth.data.model;

    public class Producto {
        private int id;
        private String nombre;
        private double precio;

        public int getId() { return id; }
        public String getNombre() { return nombre; }
        public double getPrecio() { return precio; }
    }

Reglas:
  - Los nombres de los campos DEBEN coincidir con los del JSON del backend.
  - Solo getters (para response) o solo constructor (para request).

### Paso 2: Declarar el método en ApiService.java

Abrí `data/ApiService.java` y agregá dentro de la interfaz:

    // Ejemplo: listar todos los productos
    @GET("api/productos/")
    Call<List<Producto>> getProductos();

    // Ejemplo: crear un producto
    @POST("api/productos/")
    Call<Producto> crearProducto(@Body Producto producto);

    // Ejemplo: obtener uno por ID
    @GET("api/productos/{id}/")
    Call<Producto> getProducto(@Path("id") int id);

    // Ejemplo: modificar
    @PUT("api/productos/{id}/")
    Call<Producto> actualizarProducto(@Path("id") int id,
                                      @Body Producto producto);

    // Ejemplo: eliminar
    @DELETE("api/productos/{id}/")
    Call<Void> eliminarProducto(@Path("id") int id);

Anotaciones disponibles:
  - @GET("ruta/")              → obtener datos
  - @POST("ruta/")             → crear
  - @PUT("ruta/{id}/")         → modificar
  - @DELETE("ruta/{id}/")      → eliminar
  - @Body MiClase obj          → el objeto va en el cuerpo (JSON)
  - @Path("id") int id         → reemplaza {id} en la URL
  - @Query("nombre") String n  → agrega ?nombre=valor en la URL

IMPORTANTE:
  - La ruta NO empieza con "/". Es "api/productos/", no "/api/productos/".
  - NO borrar métodos de otros. Si hay conflicto de merge, AVISAR.

### Paso 3: Llamarlo desde la Activity

    RetrofitClient.getApi(this)
        .getProductos()
        .enqueue(new Callback<List<Producto>>() {
            @Override
            public void onResponse(Call<List<Producto>> call,
                                   Response<List<Producto>> response) {
                if (response.isSuccessful() && response.body() != null) {
                    List<Producto> productos = response.body();
                    // Mostrar en el RecyclerView...
                }
            }

            @Override
            public void onFailure(Call<List<Producto>> call, Throwable t) {
                Toast.makeText(MiActivity.this,
                    "Error: " + t.getMessage(),
                    Toast.LENGTH_SHORT).show();
            }
        });

7. MAPEO DE ENDPOINTS DE LA API (tambien estan en el repo backend--> database)
================================================================================

Autenticación:
  POST    /api/auth/login/                     → login(email, password)
  POST    /api/auth/refresh/                   → refreshToken(refresh)
  GET     /api/auth/me/                        → getPerfil()
  POST    /api/auth/register/                  → registerPublic(username, nombre, apellido, email, password) : (auto-registro público, fuerza rol Empleado)

Usuarios:
  GET     /api/auth/usuarios/                  → getUsuarios()       [admin]

  GET     /api/productos/?codigo_barras=XXX    → buscarProductoPorCodigo(XXX)  [búsqueda por código]

Rubros:
  GET     /api/rubros/                         → getRubros()

  GET     /api/rubros/{id}/                    → getRubro(id)
  PUT     /api/rubros/{id}/                    → actualizarRubro(id, r)
  DELETE  /api/rubros/{id}/                    → eliminarRubro(id)

Marcas:
  GET     /api/marcas/                         → getMarcas()

  GET     /api/marcas/{id}/                    → getMarca(id)

Ventas:

7.b REGLAS IMPORTANTES DE LA API
================================================================================

### Paginación

Los endpoints de listado (`/api/productos/`, `/api/ventas/`, etc.) están
paginados en bloques de 10. La respuesta tiene esta forma:

    {
        "count": 22,
        "next": "http://.../api/productos/?page=2",
        "previous": null,
        "results": [ { ...producto... }, ... ]
    }

⚠️ Si tu endpoint devuelve una lista paginada, el modelo Java tiene que
   leer `results` (no el array directo).

### Precios como string

`precio_costo` y `precio_venta` se devuelven como STRING, no como número:

    "precio_venta": "900.00"    ← string
    "precio_venta": 900.00      ← número (NO)

En Java, si necesitás hacer operaciones, parsealos con Double.parseDouble().

### Roles

- **Administrador**: ve todo, puede eliminar productos y ventas, gestiona usuarios.
- **Empleado**: ve catálogo, crea/edita productos, registra ventas.
  NO puede: gestionar usuarios, eliminar productos, ver la lista de ventas.

El rol se obtiene de `GET /api/auth/me/` como `"role": "Administrador"` o `"role": "Empleado"`.
Los auto-registrados (POST /api/auth/register/) son siempre Empleado.

8. MANEJO DE ERRORES
================================================================================

Los errores se manejan en dos lugares:

### onFailure
Errores de RED (no llegó al servidor):
  - ConnectException        → "No se pudo conectar al servidor"
  - SocketTimeoutException  → "Tiempo de espera agotado"
  - UnknownHostException    → "Servidor no encontrado"

### onResponse con !isSuccessful()
Errores HTTP (el servidor respondió con error):
  - 400 → datos inválidos
  - 401 → no autenticado / token expirado
  - 403 → sin permisos
  - 404 → recurso no encontrado
  - 500 → error del servidor

Para manejar el código HTTP:

    if (!response.isSuccessful()) {
        int code = response.code();
        String msg = "Error " + code;
        if (code == 401) msg = "Sesión expirada";
        if (code == 403) msg = "No tenés permisos";
        // ...
        Toast.makeText(this, msg, Toast.LENGTH_SHORT).show();
    }

9. TOKENS JWT - ¿CÓMO FUNCIONAN?
================================================================================

Cuando el usuario hace login, el backend devuelve dos tokens:

  - access:  dura 1 hora. Se usa en cada petición.
  - refresh: dura 1 día. Sirve para pedir un access nuevo.

### Flujo automático

El AuthInterceptor lee el access token de TokenManager y lo agrega
a cada petición automáticamente. Vos no tenés que hacer nada.

### Después de 1 hora

El access vence y el backend devuelve 401. Acá hay dos opciones:

  Opción A (simple): redirigir al login.
  Opción B (completa): usar el refresh para obtener un access nuevo.

Actualmente implementamos la Opción A (o el backend puede extender
la duración: en web lo hicimos mediante un modal con opcion "si" o "no").

### Logout

El logout limpia todo (tokens + username + rol):

    new TokenManager(this).clear();
    startActivity(new Intent(this, LoginActivity.class));
    finish();

El backend no tiene sesión que cerrar (es stateless con JWT).

### TokenManager también guarda el rol

Además de los tokens, `TokenManager` guarda:

  - `getUsername()`   → nombre de usuario (para "Bienvenido/a, X")
  - `saveRole(role)`  → guarda el rol ("Administrador" / "Empleado")
  - `isAdmin()`       → true si el usuario es Administrador
  - `isEmpleado()`    → true si el usuario es Empleado

Se usan para mostrar/ocultar botones según el rol.

10. PREGUNTAS FRECUENTES
================================================================================

### ¿Por qué no funciona desde mi celular?
Revisá en este orden:
  1. ¿La URL en local.properties es https://librerianazareth.alwaysdata.net/?
  2. ¿Tu celular tiene internet (datos móviles o Wi-Fi)?
  3. ¿Podés abrir https://librerianazareth.alwaysdata.net/api/ en el navegador del celular?
  4. ¿Hiciste Clean + Rebuild después de cambiar local.properties?
  5. ¿BuildConfig.java muestra la URL correcta?

### ¿Por qué me da error 401?
  - No te logueaste todavía, o el token expiró.
  - Solución: volvé a loguearte, o implementá refresh token.

### ¿Por qué me da error de red "CLEARTEXT not permitted"?
  - Antes pasaba porque el backend local usaba http://.
  - Ahora con https:// de AlwaysData NO debería pasar.
  - Si lo ves, avisá al equipo.

### ¿Puedo modificar RetrofitClient?
NO. Es infraestructura compartida. Si necesitás cambiar algo,
avisá al equipo para que todos sepan.

### ¿Puedo modificar AuthInterceptor?
NO. Es infraestructura compartida. Si necesitás cambiar algo,
avisá al equipo para que todos sepan.

### ¿Puedo modificar ApiService?
SÍ, pero solo AGREGANDO métodos. Nunca borres los de otros.
Si hay conflicto de merge, AVISAR.

### ¿Puedo agregar modelos?
SÍ. Creá nuevas clases en data/model/.

### ¿Puedo usar el backend local en vez de AlwaysData?
SÍ, pero solo para pruebas. Ver sección 4.b.
Recordá volver a la URL de AlwaysData cuando termines.
